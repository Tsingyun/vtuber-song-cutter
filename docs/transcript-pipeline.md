# 直播内容转录：接入设计（上游优先、独立管线备用）

> 已实现：``songcut/transcript_hub.py``（盘点 / 定位 / 健康检查 / 归一化 / 降级编排）
> 实测命令：`--scan`、`--date 2026-09-25`（复用成功）、`--date 2026-09-27`（正确降级）

---

## 一、先说结论

**90% 以上的场景完全不需要自建转录。** 上游已经攒了 **61 场**现成转录，近期 11 场是全自动流水线产出、
时间轴与录播 0 点对齐、覆盖度接近 100%。真正需要自建的只有一种情况：**有录播视频，但上游没有对应转录**。

## 二、可复用转录资产盘点（实证数据）

### 2.1 三处来源

| 来源 | 位置 | 份数 | 覆盖 | 时效 |
|---|---|---|---|---|
| **A. 上游主目录（主力）** | `<srt_dir>\*.srt` | **11** | 2026-09-17 ~ 2026-09-28 | 直播结束后 **约 4–8 小时**自动产出（凌晨 04:00 左右落盘） |
| **B. 上游元信息（辅助校验）** | `<srt_dir>/../TXT\*.txt` | 11（与 A 一一对应） | 同 A | 同 A |
| **C. 历史档案** | `<recording_root>/历史录播 转文字\*.srt` | **50** | 2024-06-01 ~ 2024-07-31 | 2025-09 归档，一次性产物 |

### 2.2 数据格式

**A. SRT（主力，下游直接吃）**
```
1
00:04:00,550 --> 00:04:11,930          ← 时间轴 = 录播视频 0 点起算（首句在 4 分左右 = 开播前的等待段）
hello hello,晚上好呀，你好你好你好，hello有音量呢。
```
- 引擎：FunASR `SenseVoiceSmall` + `fsmn-vad` + `punc_ct-transformer`（上游 `scripts/transcribe.py`）
- 单场规模：约 600–1200 条、3.4–5.1 小时、130–190 KB

**B. TXT（只用来做交叉校验，不喂下游）**
```
# 转写日志
# 文件名: 20260925-....mp3
# 转写时间: 2026-09-26 04:04:43
# 音频时长: 16374s (04:32:54)
# 文本字数: 43629
# 分句数量: 1061     ← 与 SRT 条目数对账，用来发现"转录被截断"
```

### 2.3 覆盖质量抽检（工具实测）

| 场次 | 条目 | 字幕跨度 | 首句 | 大空白(>5min) |
|---|---|---|---|---|
| 09-25 中秋场 | 1061 | 4.48h（录播 4.55h，**覆盖 99.9%**） | 241s | **有 1 处 6.0 分钟** |
| 09-28 周一 | 1187 | 5.07h | 369s | 无 |
| 09-26 | 830 | 3.41h | 584s | 无 |
| 09-20（第 3 场） | 381 | 1.66h | 0s | 无 |

> ⚠️ **09-25 那处 6 分钟空白是真实存在的信息缺口**（VAD 漏检或真静音）。若某首歌正好落在这段里，
> 歌词线索会缺失——健康检查会把它记下来，供人工判断是否要重转。

### 2.4 ⚠️ 最大的认知落差：转录覆盖 ≫ 视频覆盖

| 资源 | 实际可用 |
|---|---|
| 转录（有文本） | **61 场** |
| 录播视频（能切片） | **仅 2 天**：`2026-09-25`（完整 8.7GB）、`2026-09-28`（**还在下载**，当前是 `.part.mp4`） |

**所以瓶颈从来不是转录，是视频。** 有转录没视频的场次，转录照样能复用（用来找歌名、对歌词、定时间段），
但出不了片——那属于"先补录播"的问题，不属于"要不要自建转录"的问题。

### 2.5 哪些能完全复用、哪些必须自建

| 场景 | 处理 | 是否自建转录 |
|---|---|---|
| 有录播 + 上游有对应转录（如 09-25） | **100% 复用**，下游零改造 | ❌ 不需要 |
| 有录播 + 上游转录缺失 | 走自建（调 video-content-pipeline） | ✅ 需要 |
| 有录播 + 上游转录不完整（条目少/覆盖<60%/时间轴不对齐） | 上游版本留档，**触发重转** | ✅ 需要 |
| 有录播 + 上游产出超时（等 N 小时仍无） | 超时即自建 | ✅ 需要 |
| **无录播**（无论有没有转录） | 转录可复用做文本分析；**切片前先补录播** | ❌ 不该跑（没输入源） |
| 历史档案（2024 年 50 场） | 只有文本，可做歌名/歌词检索库 | ❌ 不需要 |

## 三、降级触发条件与切换逻辑

### 3.1 六道健康检查（= 降级触发条件）

| ID | 检查项 | 触发降级的门槛（可调） | 判定 |
|---|---|---|---|
| `E_EXISTS` | 有没有该场次的转录文件 | 0 条 | **硬失败** |
| `E_AXIS` | 时间轴是不是录播 0 点 | 首句 > 1800s 视为轴不对齐 | **硬失败** |
| `E_VOLUME` | 条目数够不够 | < 50 条 | **硬失败** |
| `E_COVERAGE` | 字幕跨度 / 录播时长 | < 60% | **硬失败** |
| `E_GAP` | 有没有超长空白 | 单处 > 600s | ⚠️ 软告警（记录，不单独触发） |
| `E_META_MATCH` | SRT 条目 vs TXT 元信息 | 差异 > 2% | ⚠️ 软告警 |
| `E_FRESH` | 转录是否早于录播版本 | 早于录播 6 小时以上 | ⚠️ 软告警（版本错配风险） |

**切换规则：任一硬失败 → 降级；软告警只记录、不降级**（因为直播本来就可能长时间静音或有 BGM）。

### 3.2 切换逻辑（一句话版）

```
找上游转录 → 健康检查
   ├─ 通过           → 直接复用，落统一格式（不自建）
   ├─ 硬失败/没有     → 检查本地有没有录播视频
   │                    ├─ 有  → 触发自建管线（video-content-pipeline）
   │                    └─ 无  → 不自建，报"请先获取录播"后停止（避免空转）
   └─ 上游未产出（等待场景）→ 等待 N 小时（默认 6h），超时再走上面那条
```

**关键约束：绝不与上游并行跑。** 上游可用时自建管线**根本不启动**；自建只在上游确认不可用之后才跑，
且产出写进同一套统一格式，**下游完全感知不到来源差异**。

### 3.3 统一输出契约（对下游一致）

无论来自上游还是自建，都落这两份东西：

**① `transcript-<场次>.json`**（富格式，供需要元信息的环节）
```json
{
  "schema": "transcript/v1",
  "date": "2026-09-25",
  "session": "20260925-陪你这个猪擒住中秋节！ 2026年09月25日20点场",
  "source": {"kind": "upstream|fallback", "path": "...", "engine": "...", "produced_at": "..."},
  "timebase": {"origin": "recording", "unit": "second", "offset_sec": 0.0},
  "segments": [{"i": 0, "start": 240.55, "end": 251.93, "text": "hello hello,晚上好呀…"}],
  "stats":   {"count": 1061, "first_sec": 240.55, "last_sec": 16369.2, "span_sec": 16128.6},
  "health":  {"ok": true, "checks": [...]}
}
```

**② `transcript-<场次>.srt`**（归一化 SRT，UTF-8，时间轴 = 录播 0 点）

> ② 是给现有下游（歌切的 `parse_srt`）准备的：**格式与上游 SRT 完全一致，现有代码零改造即可吃**。
> 这是"对下游一致"最省事的做法——不强迫下游改解析器。

## 四、整体接入设计

### 4.1 模块职责

| 模块 | 职责 | 复用/自建边界 |
|---|---|---|
| **T1 盘点器** `scan_upstream` | 扫描三处来源，输出"有哪些场、多少条、覆盖多久、有没有缺口" | 纯读取上游，无自建 |
| **T2 定位器** `locate_upstream` | 按日期（可含场次）找对应 SRT；支持一天多场 | 纯读取上游 |
| **T3 健康检查** `health_check` | 六道检查 → 判定"复用 / 降级" | 判定逻辑自建（很轻，非等价实现） |
| **T4 归一化** `build_transcript` + `write_outputs` | 统一成 transcript/v1 + 归一化 SRT | 轻量格式转换，非转录能力 |
| **T5 降级编排** `fallback_plan` / `run_fallback` | **只做命令编排**：调 video-content-pipeline 的 `transcribe.py` | ⚠️ **不自己写 FunASR 调用** |
| **T6 台账** | 记录本场用了哪条路、检查结果、产出路径 | 自建（日志级） |

### 4.2 运行时数据流

```
        ┌── 上游 SRT（11 场） ──┐
        ├── 历史档案（50 场） ──┤
        └── 上游 TXT 元信息 ────┘
                  │  T1 盘点 / T2 定位（按日期+场次）
                  ▼
            T3 健康检查（6 项）
              │                 │
        通过 ─┘                 └─ 失败
          │                        │
          ▼                        ▼
   T4 归一化 ─────────►   有本地录播？ ──否──► 停止并提示"先补录播"
          │                      │是
          │                      ▼
          │            T5 调 video-content-pipeline
          │            （FunASR 转录 → SRT）
          │                      │
          └──────────┬───────────┘
                     ▼
        transcript.json + 归一化 .srt（同一契约）
                     ▼
        下游：歌切 / 总结 / 检索（只认契约，不认来源）
```

### 4.3 复用与自建的边界（一句话划清）

- **复用侧**：转录这件"重活"本身（模型下载、GPU 推理、VAD、标点）——**永远复用**；上游优先，其次复用已存在的通用 Skill。
- **自建侧**：只自建**外围的胶水**——找文件、验健康、转格式、记台账、决定要不要降级。
- **绝不自建**：第二套 FunASR 调用实现（这就是"不与上游并行维护两套等价实现"的落点）。

| # | 问题 | 我的建议 |

| ① | 历史档案（2024 年 50 场）要不要纳入统一索引？ | **纳入但只做文本检索**（歌名/歌词线索），不参与切片（无视频） |

| ⑤ | 09-28 那场视频还在下载（`.part.mp4`），下载完是否自动触发？ | 建议加一个"视频就绪"检查，`.part` 存在时不启动切片 |

## 六、已知坑位

1. **一天多场**：09-20 有"20 点场"和"23 点场（第 3 场）"两份转录 → **不能只用日期做唯一键**，必须按场次文件名区分（工具已按场次遍历）。
2. **时间轴基准不同**：近期档案首句在 241s（录播 0 点含开播前等待），历史档案首句在 0s → **跨源混用会整体错位**，归一化时会把基准写进 `timebase` 字段。
3. **6 分钟空白**（09-25 实测）→ 该区间内没有歌词线索，歌切遇到时要能标注"此段无字幕"而不是静默失败。
4. **版本错配**：转录 mtime 早于录播 mtime（如 09-26 是次日 13:06 补跑的）→ 可能转录的是旧版录播，`E_FRESH` 会告警。
5. **中文/特殊字符文件名**（`！`、`（）`）→ 传参和 glob 都要小心，工具统一用 Python 内部处理，不走 shell 拼接。
6. **未下载完的视频**（`.part.mp4`）→ 必须跳过，否则对着半个文件转录/切片（工具已过滤）。
7. **不要因为"想更可控"就去写第二套转录**——这正是本次架构要避免的事；要改就改上游或改通用 Skill，让所有下游一起受益。
