# 歌切系统：独立化方案设计（分阶段落地）

> 目标：输入一段数小时的直播录播 → 自动找出主播在哪些时段唱歌、唱的是哪几首 →
> 每首单独切出 → 用现有播放器页面预览确认 → 导出 1080P60 成品视频。
>
> 本文只讲方案与决策，不含代码。所有"现役"标注都指今天实证过的 `本仓库根目录` 实现。

---

## 零、一句话总览

把现在这套"散在录播总结项目下游"的歌切能力，抽成一个**独立的小流水线**：
**它自己有输入（录播 + 可选歌单）、自己有中间产物（候选段清单）、自己有出口（成品视频 + 台账）**，
与上游"直播总结"只通过**文件契约**打交道（录播 MP4、可选 SRT 字幕），不再互相 import 代码。

---

## 一、模块划分与数据流转

### 1.1 解耦边界在哪（关键决策点 ①）

现状是：歌切直接读上游的 `<srt_dir>\*.srt` 和它的 `config.json`（连 LLM 的 key 和代理都复用人家的）。这属于**硬耦合**。

建议的边界：**只保留"文件级契约"，断开"代码级依赖"**

| 契约 | 内容 | 上游是否必须存在 |
|---|---|---|
| 录播视频 | `录播根目录/YYYY-MM-DD/*.mp4`（音轨无损，1080P60） | 必须 |
| 转写字幕（可选） | `*.srt`（FunASR 产物） | **可选**，缺失走无 ASR 路线 |
| 演唱歌单（可选） | 当日歌名列表（在线表格 / 手工 CSV / 歌曲库） | **可选**，但强烈建议有 |
| 自有配置 | 新项目自己的 `config.json`（ffmpeg 路径、LLM key、代理、输出目录） | 必须（自己管自己的） |

> ⚠️ **坑 1**：现在 `song_cutter.py` 的 `main()` 在没有 SRT 时直接抛错终止。独立化后这一步必须改成"警告 + 降级"。
> ⚠️ **坑 2**：LLM 的 key/代理现在读的是上游 `config.json`，上游一改配置歌切就跟着坏。抽离后必须自带配置。

### 1.2 七个模块（输入 → 输出）

```
   录播MP4 ─┐
   可选SRT ─┼─► ① 素材接入 ──► 音频轨(单声道wav，按需分段抽) + 录播元信息
   可选歌单─┘                        │
                                     ▼
                        ② 唱歌候选段检测 ──► candidates.json
                           [{start, end, 评分, 信号明细}]     ← 人工可看可改
                                     │
                                     ▼
                        ③ 边界精修 ──► refined.json
                           [{cut_start, cut_end, onset, 依据}]
                                     │
                                     ▼
                        ④ 歌曲识别 ──► identified.json
                           [{title, 原唱, P主, 置信度, 判据来源, 需人工?}]
                                     │
                                     ▼
                        ⑤ 歌词/时间轴/封面 ──► lrc + cover + 时间轴来源标记
                                     │
                                     ▼
                        ⑥ 预览确认 ──► 预览截图 / 短预览片（人工拍板）
                                     │
                                     ▼
                        ⑦ 渲染导出 ──► 成品MP4 + manifest.json（台账）
```

**每个模块的输入输出一眼看懂版：**

| 模块 | 吃进去什么 | 吐出来什么 | 现役可复用度 |
|---|---|---|---|
| ① 素材接入 | 录播 MP4（+可选 SRT/歌单） | 音频轨、时长、分辨率/FPS、歌单列表 | 现役（`ffprobe` + `find_video`），SRT 改成可选即可 |
| ② 唱歌候选检测 | 音频轨（几小时） | 疑似唱歌的时间段清单 + 每段评分 | **需新建**（现役没有盲检能力，粗定位靠 LLM 读字幕） |
| ③ 边界精修 | 候选段 + 音频轨 | 精确到 0.1s 的起止点 | 现役（`wave_refine` + `onset_v2`），几乎可直接搬 |
| ④ 歌曲识别 | 精修后的音频段 + 歌单 +（可选）字幕 | 歌名 + 原唱/P主 + 置信度 | 部分现役（歌单比对、LLM 联网核对、chroma DTW） |
| ⑤ 歌词时间轴 | 歌名 + 成品音频 | 对齐后的 LRC + 封面 + 时间轴来源标记 | 现役（`lyrics_fetch` / `lyrics_sync` / `lyric_align` 三级降级） |
| ⑥ 预览确认 | LRC + 封面 + 音频 | 预览画面（截图或短片） | 现役（`renderer/player/index.html`） |
| ⑦ 渲染导出 | 确认后的素材包 | 1080P60 MP4 + 台账 | 现役（`render_song.cjs` + ffmpeg 混流 + ffprobe 校验） |

**中间产物全部落 JSON** 是这套设计的核心：任何一步都能被人工改一下再继续往下跑，不用从头重来。

## 二、唱歌检测：几小时音频里怎么区分"唱 / 说 / 放音乐 / 背景音乐"

### 2.1 先说清楚四类东西各是什么样

| 类别 | 听感特征 | 机器看得见的信号 |
|---|---|---|
| **主播唱歌** | 有旋律、音高连续、一句能持续 1–3 秒、通常有伴奏垫底 | 基频清晰且连续、谐波强、能量平稳不忽高忽低、持续时间长 |
| **主播说话** | 音高乱跳、音节短促、有停顿 | 基频存在但抖、谐波弱、能量忽强忽弱、短句多 |
| **纯音乐/BGM**（主播没唱） | 有旋律但没有人声 | 能量平稳、有节奏，但**人声频段没有稳定基频** |
| **背景垫乐 + 聊天** | 音乐连续、人声断续 | 音乐信号强 + 人声信号弱且断续 |

### 2.2 思路：不要指望一个指标判生死，用"打分 + 投票"

推荐**三层递进**，先宽后严：

**第一层：粗筛（宁可多，不能漏）**
- 用轻量 VAD 或能量包络，把整段录播切成"有声音 / 没声音"；
- 把连续有声 ≥ 30 秒的段挑出来当候选（一首歌最短也 40 秒，聊天很难连续高能 30 秒不停）。
- 目的：把 3 小时的音频压成十几个候选段，后面的重活只在这些段上跑。

**第二层：给每个候选段打"像不像唱歌"的分（0–100）**
并行看四个信号，各自打分再加权：

| 信号 | 怎么看 | 说明 |
|---|---|---|
| 基频连续率 | 用 pyin/CREPE 提取音高，看有多少比例的时间点存在稳定音高 | 唱歌通常 60%+，说话 30% 上下 |
| 谐波强度（HNR） | 谐波与噪声之比 | 唱歌高，说话低 |
| 音高平稳度 | 相邻音高变化是否平缓（不是乱跳） | 旋律 vs 语调 |
| 时长与连续性 | 持续 ≥40s、中途无长静音 | 排除"随口哼两句" |

**第三层：与已知原曲比对（最强的一票）**
- 如果歌单里已经知道当天唱了 A/B/C 三首，那就拿这三首的原曲音频去录播里做 chroma 匹配；
- 匹配上了 = 这一票几乎可以一锤定音（现役 DTW 实测误差 0.02 秒）。

**综合判定**：`总分 = 0.4×歌声特征分 + 0.4×原曲匹配分 + 0.2×时长合理性`；超过阈值才进切片环节，落在灰区的标"待人工确认"。

### 2.3 精度取舍（要提前接受现实）

| 做法 | 好处 | 代价 |
|---|---|---|
| **宽进（阈值调低）** | 几乎不会漏掉真唱的歌 | 会多出一堆候选，需要人工或后续环节筛掉 |
| **严进（阈值调高）** | 出来的基本都是真货 | 清唱、冷门曲、编曲差异大的翻唱容易被漏 |

**建议：宽进 + 中间产物可人工改**。理由：漏一首歌 = 这首歌永远出不了片；多一个候选 = 人工点一下删掉，成本极低。

### 2.4 已知会踩的坑

- ⚠️ **坑 3（实测）**：直播音频经过重度压缩，"绝对音量"失去区分度——说话可能比唱歌还响。**任何绝对阈值判静音/判唱歌的做法都会失效**，必须用相对量（分位数、对比度、相对底噪）。现役 `onset_v2` 就是因为这个才用 `底噪+6dB`、`说话能量−45/35/25dB` 这种相对阈值。
- ⚠️ **坑 4**：Rap / 念白 / 情绪激昂的说话会被判成唱歌（基频也连续）。缓解：要求时长 ≥40s 且中途无明显停顿。
- ⚠️ **坑 5**：电子伴奏很响时会盖住人声特征 → 歌声打分偏低。缓解：引入人声分离（见决策点 ④）。
- ⚠️ **坑 6**：同一首歌一晚上唱两次（返场）→ 匹配会给出两个峰，要去重保留两个而不是合并成一个。
- ⚠️ **坑 7（实测）**：结尾渐弱的副歌/尾奏，能量会低到被误判成"掌声/说话"——寄明月案例里差点把整段尾奏切掉。**尾点判断不要只看能量阈值**，要配合原曲结束点（DTW）交叉验证。

## 三、歌曲识别：判断唱的是哪首

### 3.1 四条线索，按性价比排序用

| 优先级 | 线索 | 怎么做 | 靠谱程度 |
|---|---|---|---|
| **1** | **歌单**（最香） | 在线表格《今天唱什么》/ 你维护的歌曲库，当天唱了哪几首是已知的真值 | 最高，且零成本 |
| **2** | **音频比对** | 拿歌单里的歌去网易云下原曲 → 与录播做 chroma 匹配，谁对上就是谁 | 高（有原曲时 ±0.1s） |
| **3** | **字幕文本 + 联网核对** | 读 SRT 找"报歌名"的话 + 歌词碎片，交给带搜索的 LLM 核实 | 中高，但依赖 ASR |
| **4** | **听音识曲**（Shazam/ACRCloud 类） | 音频指纹直接问服务 | **不推荐**：术力口/同人曲基本认不出，还付费 |

**推荐组合**：`歌单（如果有）→ 音频比对确认 → 都拿不到再上字幕+LLM → 还不行就标"未知"等人确认`。

### 3.2 成功 / 失败分别怎么办

| 情况 | 处理 |
|---|---|
| 歌单有 + 音频比对成功 | 直接出片，歌名取歌单原名（**不要取网易云匹配到的近似名**，避免翻唱当原唱） |
| 歌单有 + 比对失败 | 仍按歌单出片，但标记"未验证"，预览时重点看歌词是否贴得上 |
| 歌单没有 + 字幕+LLM 判定 | 出片，标"LLM 判定，置信度 X"，建议人工看一眼 |
| 全部失败 | **两种选择（决策点 ⑤）**：① 不出片，进"待确认队列"；② 出片但歌名写"未知曲目 HH:MM"，事后补 |
| 原唱/翻唱分不清 | **必须联网核实**（你之前明确要求过）。术力口曲还要同时标演唱者与 P 主 |

### 3.3 人工确认环节：必须有，但要做得轻

建议做一个**极简确认面板**（一个网页表格即可，不必写后台）：

```
[✓] 01:23:45-01:27:38  寄明月   置信度 0.95  来源: 歌单+音频比对   [预览] [改歌名] [删掉]
[?] 02:10:02-02:14:11  未知     置信度 0.41  来源: 歌声特征        [预览] [填歌名] [删掉]
```

- 高置信度的**默认勾选**，人工只看灰区；
- 「预览」按钮直接调播放器页面出一张截图（就是你现在在用的那套）；
- 确认结果回写 `identified.json`，后面所有环节都读它。

> ⚠️ **坑 8**：歌名里的**不间断空格（NBSP）、波浪号、全半角**会导致后续匹配全部失联——你之前已经因此修过 16 首歌。识别结果写入前必须做一次标准化。

## 四、切片与导出

### 4.1 起止点怎么定（两道关）

**起点（最容易错）**
1. LLM/粗筛给的起点通常**偏晚**（实测偏晚约 28 秒，会把渐强前奏吞掉）；
2. 所以必须**往回多搜一段**（现役往回搜 60 秒）；
3. 在回搜窗里找"说话段 → 静音谷 → 能量回升"这个三段式结构，取能量真正爬起来的那一刻；
4. 再往前留一点余量（现役至少 1.2 秒），最后保证片头有 ≥0.8 秒静音（不够就补）。

**终点（也容易错）**
1. 波形包络找"音乐结束后的静音"；
2. 同时用原曲 DTW 算出的"伴奏真实结束时刻"交叉验证；
3. 取两者的合理值，**再往后留 1.6 秒余韵**；
4. 尾部做 1.2 秒淡出，防止硬切爆音。

> ⚠️ **坑 9**：不要只靠包络判终点。寄明月案例里末段渐弱副歌被包络误判成掌声，差点整段切掉。三源互证（包络 + DTW 结束点 + 字幕逐块偏移）是必需的。

### 4.2 首尾缓冲速查表

| 位置 | 留多少 | 为什么 |
|---|---|---|
| 片头静音 | ≥0.8s（不足则补） | 一进来就是伴奏会很突兀 |
| 起点余量 | ≥1.2s 自然起手 | 给主持人报幕后的呼吸感 |
| 尾部余韵 | +1.6s | 收尾不干硬 |
| 尾淡出 | 1.2s | 防爆音 |
| 整首长度 | 40–900s 合理区间 | 超出要报警人工看 |

### 4.3 歌词时间轴：三级降级（现役机制，直接沿用）

```
① 精确：原曲锚点 + DTW 速度比      （误差 0.02s，首选）
② 降级：字幕(ASR) 配对 + 常数偏移  （误差 0.3–1.5s）
③ 兜底：直接用原版 LRC 时间轴      （误差 1–3s，翻唱编曲不同会更飘）
```
用哪一级要**记进台账**，方便事后知道哪首歌的歌词可信、哪首要重做。

**卡拉OK逐句填充**（你现在在用的）：句尾需要一个"这句唱完了"的时刻。三个来源，推荐度从高到低：
1. 网易云**官方逐字歌词**（VIP 逐字 klyric）经 DTW 映射 —— 最准；
2. ASR 字幕的句尾 + 0.45 秒余韵 —— 次准（字幕组常把好几句合并成一条，要取组尾）；
3. 按字数估算 —— 兜底。
**关键**：句与句之间的间奏/换气**不能摊进填充进度**，否则会出现"最后一句推进过慢"（这正是上次修的问题）。

### 4.4 怎么复用现有播放器页面（你已调过多版的那套）

```
工坊页面 `renderer/player/index.html`  （你在这调版式、调动效）
        │  _make_prod_player.py（8 处幂等补丁，自动生成）
        ▼
生产页面 player/index.html      （渲染专用，不要手改）
        │  render_song.cjs（Playwright 无头 + WebCodecs 逐帧编码）
        ▼
无声视频 → ffmpeg 混入音轨 → 成品
```

- 素材通过一份 `job.json` 注入（歌名/原唱/P主/标签/译名/歌词/封面/立绘/输出路径）；
- **预览与出片用的是同一套页面**，所以你在预览里看到的效果 = 成片效果，不会跑偏。

> ⚠️ **坑 10（实测，很容易再踩）**：图片如果用本地文件路径加载，会"污染"画布，导致编码器报错拒绝工作。**所有贴图必须转成 dataURL 字符串注入**（封面、立绘、小鸟、水印都一样）。
> ⚠️ **坑 11**：画面里画文字前必须显式设置颜色，否则会继承上一帧残留的颜色，出现"白字隐形"（右上角 TRACK 文字就这么消失过）。

### 4.5 1080P60 导出的关键参数

| 项 | 参数 | 备注 |
|---|---|---|
| 画面 | 1920×1080 @ 60fps | 逐帧渲染，虚拟时钟驱动，不受实时播放速度限制 |
| 视频编码 | H.264（WebCodecs 硬编优先，软编兜底） | 编码器选型自动 |
| 中间音频 | MP3 192k（`libmp3lame`）+ 尾部 1.2s 淡出 | 供页面渲染同步用 |
| 混流 | `-c:v copy -c:a aac -b:a 192k -movflags +faststart -shortest` | 视频流直拷不二次编码，画质无损、速度快 |
| 校验 | ffprobe 核对分辨率/帧率/时长，与预期时长偏差 >0.5s 报警 | 现役实测偏差 0.00s |
| 清理 | 成品校验通过后再删中间 MP3 与临时文件 | 别提前删，失败没法复盘 |

## 五、落地路线（先跑通，再变强）

### M1 — 最小可用版（目标：今天这套能脱离上游独立跑起来）
- 建独立目录 + 自带配置（不再读上游 config.json）；
- SRT 改成**可选**输入（没有也能跑）；
- 保留现有全部精修/识别/渲染能力，只把"入口硬依赖"去掉；
- 歌单走"手工填一份当日歌名列表"这种最土的方式；
- 产出：一条命令从录播 → 成品。

**验收**：随便挑一场，N 首歌全部切出，时长偏差 <0.5s，歌词能对齐。

### M2 — 自动找段（目标：不再需要人工给粗区间）
- 加"唱歌候选检测"模块（VAD 粗筛 + 歌声特征打分）；
- 输出 `candidates.json`，人工可改；
- 与原曲 chroma 比对接上（有歌单时一锤定音）。

**验收**：一场直播自动找出来的候选段里，真唱的歌**一首不漏**（允许有多的）。

### M3 — 自动认歌 + 人工确认台
- 歌单自动抓取（在线表格，现役脚本可用）；
- 识别结果进确认面板（勾选/改歌名/删掉/预览）；
- 置信度分流：高的自动过，灰区等人。

**验收**：灰区占比 <30%，人工 5 分钟内能确认完一场。

### M4 — 精度与体验迭代
- 逐句卡拉OK改用官方逐字歌词；
- 收集误判样本（漏检/误检）反哺阈值；
- 同曲多次演唱去重、冷门曲兜底策略；
- 批量队列 + 断点续跑（跑一半挂了能从中断处继续）。

### M5 — 长期（可选）
- 人声分离作为疑难场景增强；
- 成品自动归档/上传；
- 统计面板（每场自动切出几首、准确率走势）。

## 七、最可能踩的坑（汇总速查）

1. 没有 SRT 就整链抛错 → 必须改成警告降级
2. 复用上游 config.json → 上游一改你就坏，必须自带配置
3. 用绝对音量阈值判唱歌/静音 → 直播压缩后失效，必须相对量
4. Rap/念白/激动说话会误判成唱歌 → 用时长 + 停顿特征过滤
5. 电子伴奏盖住人声 → 歌声打分偏低（必要时上人声分离）
6. 同一首歌返场唱两次 → 要去重保留两段
7. 尾奏渐弱被误判成掌声 → 终点必须多源交叉验证
8. 歌名里的隐藏字符（NBSP/波浪号）→ 写入前统一标准化
9. 终点只看包络会切短 → 配合原曲结束点
10. 本地图片路径污染画布导致编码失败 → 贴图全部转 dataURL
11. 画文字前没显式设颜色 → 继承残留色导致白字隐形
12. 渲染中途被安全策略中断/临时文件删不掉 → 长任务前解除会话级删除守卫、清理加容错
13. 多 P 录播没合并 → 时间轴会错位（必须是单一连续时间线）
14. 术力口曲的"原唱/翻唱/P主"标注 → 必须联网核实，不能靠自动匹配的结果直接上片
